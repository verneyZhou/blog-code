## 如何设计一个AI Agent？

我先简单介绍下这个项目的背景，背景就是当时我们的运营团队每天会处理大量重复的工单，比如：优惠券该如何使用？新人福利如何获取？订单咨询等问题，所以想做一个能智能处理这些工单的AI客服Agent，主要是想有 能对工单进行分类、RAG知识库检索、自动生成草稿回复 这些功能；

之后跟产品沟通后，我们这个客服Agent的核心工作链路主要是 工单入库、工单分类、知识库检索、草稿生成、人工审批、发送，这样一个工作流程；主要是承接我们C端用户和部门内其他平台的运营类工单查询；所以当时我们对这个Agent的定位就是一个知识库量级在千级文档以内的单Agent项目，主要面对的是"事实型问答"，更需要的是"准确的事实信息"，而不是"复杂的操作流程"。

> 在技术方案设计之前，我们也调研了目前市面上比较成熟的Agent项目；其实广泛意义上来讲，我觉得所有围绕大模型做的应用都可以算是Agent；包括ChatGPT、DeepSeek官网这种带有联网搜索功能的大模型调用是比较简单的Agent项目，像Claude Code、Codex、Trae、Cursor等等这些AI代码编辑工具，之前比较火的OpenClaw，Manus这些算是设计比较复杂的Agent项目；目前Agent这个行业也是处于一个快速迭代的时候，没有哪个Agent工具可以说能够解决所有的业务问题；而且我觉得Agent的底层原理其实不是新的东西，基本都是围绕大模型搭建的一套工程化的体系，就看这套工程适不适合自己的业务场景了；所以调研到最后，我们决定不直接使用其他像LangChain这种比较成熟的第三方框架，直接基于我们智能客服的场景自研搭建一套Agent；

目前市面上的Agent框架很多，但分析后发现其实底层的Agent结构基本都差不多，基本都是包括 上下文管理、工具系统、任务编排设计、状态和记忆、评估和观测、约束和恢复，主要是这六个模块，如果是多Agent项目还会设计Agent之间的协作；因为我们这是一个单Agent项目，就先不考虑多Agent之间的协作，所以我们从一开始设计的时候，就主要从刚才说的这六个模块去考虑，后续再做多Agent协作的升级；所以在前期我们会花比较多的时间去进行整个Agent协议数据模型的设计，这一块也是我们整个Agent项目最重要的部分；因为这一部分的设计关系到整个Agent项目的稳定性以及后续的迭代和升级；

我们的Agent协议的数据模型是围绕 从用户提交一个工单开始，到工单任务结束 整个生命周期来设计的。
当用户创建一个工单，我们会创建一个工单的长期上下文，就类似于ChatGpt中的某个单独的聊天框，这个工单上下文会跟用户id和工单id进行关联，我们叫thread对象，也可以叫session对象；它会包含这个工单的内容、主题、分类、用户ID等字段信息；
在当前工单上下文中发起一次对话会我们创建一个run对象，也可以叫做任务对象，它主要存的是某一轮对话任务的具体执行信息，它会包含当前轮次对话的任务状态、对话内容等信息；
而在每一轮对话中，在我们Agent后台其实是会执行多少步骤，比如工单分类、知识库检索、草稿生成等等，它主要存的就是每个step里面执行信息，比如模型调用情况，token消耗、耗时等等；
而每一个步骤又会有多个事件流类型，比如任务创建、步骤创建、步骤完成、草稿已生成、任务结束、任务失败等等，它其实是对应的整个Agent生命周期中各种不同类型的事件处理；它里面主要存的是当前事件类型、error信息，以及来源run_id和step_id；
所以从数据模型的层级关系来区分的话，用户创建一个工单会生成一个工单上下文，单个工单上下文会有多个对话任务，单个对话任务有多个step，而单个step又有多个事件流；除此之外，在单个对话任务中的每个step结束后我们都会生成一份Checkpoint快照信息，和artifact产物信息，这样就基本能覆盖从工单创建到工单结束所有的数据状态的管理；有了这些数据之后，我们就可以对Agent执行链路的整个生命周期进行观测和评测，也是方便后续迭代优化可以有比较准确和详细的数据做支撑；

数据模型设计完之后，在数据分层的设计上，我们单独设计一个store模块用于数据的持久化，它主要封装对sql数据库的调用，上面说的所有数据模型的读写操作都通过store模块暴露出来的方法进行调用；
同时我们也会有单独的model层用于对大模型调用的封装，单独的事件管道用于事件的写入和SSE流式事件的封装，也会封装取消信号总线，用于广播取消信号；封装RAG知识库的处理；会单独封装skill层用于skill的注册；

除此之外，我们也会单独封装Agent的runtime用于整个Agent系统的任务编排，runtime算是我们整个Agent设计最核心的部分了，刚才说的数据模型和数据分层模块最终都会归拢到runtime里进行调用，我们Agent的主要执行链路也是在这里进行编排：从接收一个对话任务，到驱动大模型进行推理，调用skill，写入step信息，检查是否需要人工审查，写入Checkpoint快照信息，循环执行不同步骤，直到对话任务完成，都是在runtime也进行设计；

之后在整个node服务启动的时候，我们会完成上述所有模块的初始化，同时也会将初始化之后的各个模块传入我们Agent的runtime里面，方便后续进行任务编排的时候进行调用；

总的来说，在我们上线的第一版本中，客服工单的处理是线性管道：分类→检索→起草→审批；Agent的任务编排逻辑就是：接受到一个对话任务，创建Thread对象、Run对象，之后通过编排层模型判断应该调哪个skill，同时要求模型返回约定的json，Agent拿到模型返回的json，取调对应skill的excute方法，执行对应skill代码逻辑；直到所有步骤都执行完毕，等待前端人工审核；审核完毕，整个对话任务执行结束。后续用户发起新对话会带上当前工单id、thread_id，重新走刚才的对话任务执行流程。

而且现在所有的数据都通过sql落库，用户每一轮的对话信息都可以在我们的B端监控平台查到，同时我们也按照我们设计的数据模型，在B端监控平台建立了一套可视化的分析工具，用于查看用户任意时间节点的对话内容信息；

## 如何设计一个B端低码平台？

简单说下项目背景，因为在团队内存在很多B端平台，运营平台、打断平台、运力平台、云控平台 等等，其他大多数平台页面基本都是CRUD类的增删改查页面，里面的页面结构基本都大多类似，表单字段的提交校验，table列表的查询；而且我们团队现在这些平台技术栈都是React，用的组件库基本都是ant-design，UI风格基本一致；在之前开发模式基本都是复制粘贴一个旧页面，然后改一改；这样时间长了后项目体积就比较臃肿，里面基本都是相似的代码不停重复。

基于这样一个背景，我们就想搭建一个可以快速产出B端CRUD页面的B端低码平台，方便开发、产品或运营可以快速搭建比较常规的B端页面。

这个项目整体是一个React + Node.js 的全栈项目，项目整体的分层架构设计从客户端到服务端分别是：视图层、协议层、物料层、基础能力、和后端服务；
视图层的就是B端页面的编辑端和展示端，也是用户直接能看到的部分，目前包含的模块主要是可视化拖拽和编辑、画布渲染、属性面板配置和页面展示这些；
协议层是整个项目最重要的部分吧，它主要是包含了渲染引擎、JSON Schema设计、事件流配置、变量系统、接口数据源管理、组件树设计，状态与数据流管理等等；
物料层就是整个平台提供的组件物料和页面模板，主要包含像input输入框、select下拉组件这一类通用的基础组件，包含筛选查询和列表展示的高级组件，还有一些业务组件和页面模板；
基础能力就是主要是权限管理、版本管理、发布机制、CI/CD工程化，这些围绕这个低码平台生在生产环境运行的底层配置；
后端服务就是整个低码平台的后端接口服务，它主要包含页面的创建、编辑、查询、展示、发布、回滚等接口，还有其他的 数据库、接口代理、jwt鉴权、这些

整体项目架构是用monorepo搭建的一个单仓库多模块的项目，编辑端和展示端是两个 Vite + React 的前端项目，编辑端通过 Zustand+immer 统计进行数据状态管理；组件物料底层还是用的antd-design，然后这个组件库基础上做二次封装，后端通过 koa + mysql 搭建；

整个平台设计过程中第一个比较核心也是比较基础的地方就是 JSON Schema 的设计；这里我是用一个大的pageData来完整的描述整个页面，里面通过config存全局配置，里面会有页面属性、样式等信息；也通过api保存接口管理、variable保存变量配置、events存事件流配置；除此之外还有elements保存整个页面的组件树结构，同时也会有一个elementsMap保存扁平化组件配置映射信息，这算是一种双轨制的数据模型设计吧：elements 只存组件id 和 它的parentId，保存的是整个页面的组件布局结构，elementsMap则扁平化的保存所有组件的配置信息，渲染的时候通过组件id索引获取信息进行渲染；

另一个比较重要的部分就是渲染引擎的设计；首先我们把渲染引擎单独抽成一个共享包，editor 编辑预览和web生产环境对外展示的时候用的是同一份代码同一个 store 定义；渲染引擎本质就是对 elements 树做一层层递归懒加载，并注入合并好的 props/events/api；对于增删改查等操作是通过设计一套事件流来进行管理编排，用户在某一行点击的行为背后挂的其实是一棵事件行为有向无环（DAG）图，里面有发请求、弹确认框、刷新表格、跳链接等等二十多种原子动作，最后会被转成链表顺序串起来执行；

对于后端的设计，就是通过 router/controller/service 三层来进行分层管理，MySQL 存的 pageData 就是一个 LONGTEXT 字符串，可以发布快照保留最近三个版本，也提供一键回滚功能；在低码平台中后端角色就是提供数据的存取服务，更多的复杂逻辑其实是在前端；





## 电商平台从商品展示到售后，如何进行设计？


电商C端从商品展示到下单、支付、售后 算是所有电商业务中比较核心的模块了吧，基本上只要做电商的都会搭建这样一套业务流程；不管是之前接触的在线教育、日化用品、零售、还是现在的打车，虽然业务形态都不一样，但其实底层的技术设计逻辑都比较类似；基本就是两方面：一个是比较良好的用户体验、一个是安全稳定的交易链路；基本上百分之80左右的研发设计都是围绕这两点去做的；

先从用户体验上来说吧，电商 C 端的用户体验本质上就是一件事：用户永远不能看到白屏，并且永远有反馈。像商品首页这种包含轮播图、推荐位、商品列表、秒杀入口、分类导航的多模块页面，核心思路基本都是围绕“动静分离、分级加载”这个方向去优化。能静态化的一律推到CDN，用户打开瞬间就有内容，接口全挂了也不会白屏。首先是静态骨架屏的展示，之后再是动态数据的加载，动态数据按优先级分P0、P1、P2：P0是首屏必须的，比如轮播图、秒杀入口，资源请求最好聚合为一个接口，因为需要考虑弱网多个http请求的往返时间；P1像商品列表，滚到才加载,还有比如秒杀倒计时启动；P2像个性化推荐、分类导航、埋点这些，空闲再加载。还有像商品都会有很多图片，能用WebP就用webP、低清图占位，固定宽高比防止布局抖动、首屏图预加载、其他不需要首次展示的懒加载。二次进入直接走Service Worker缓存，秒开。还有就是弱网分级处理：弱网下强制接口聚合、图片降清晰度、关闭动效，断网展示离线缓存。
用户体验指标量化上，我们会用按网络和机型分桶，看75分位和90分位的数据，目标就是：正常网络下首页 FCP 小于 1s、LCP 小于 2 秒，弱网 4G 下 LCP P75 小于 3 秒，二次进入小于 300 毫秒。

另一个比较重要的模块是秒杀，秒杀业务比较重要的问题就是：倒计时要准、按钮要防重、流量要削峰。倒计时的时间是从服务端拿权威时间算offset，再用performance.now()这种单调时钟来走，这样用户改时间、浏览器休眠都不影响，还有就是客户端倒计时归零不等于能下单，能不能抢永远以服务端时间窗、资格令牌、库存为准；dom更新上用requestAnimationFrame替代定时器进行更新；按钮防重上我不会在按钮上加防抖，因为这样会吃掉用户的合法重试操作，我会用状态锁加幂等Key，点击瞬间按钮锁死，同时生成一个UUID，同一次操作的重试复用同一个Key，后端碰到重复Key直接返回第一次的结果。既防了连点，又不误伤正常重试。
秒杀抢购的瞬间可能会出现用户疯狂连点的情况，这时会出现瞬时的流量高并发，流量削峰主要是后端做并发限制，但前端也可以配置做一些处理，我们会在开抢前一两分钟预发资格令牌，没令牌的请求网关直接拦；抢购先进排队，SSE 叫号，把洪峰变成可控的流；同时对于请求失败的情况，用户也可能会不停点击重试，前端会通过随机抖动来分散重试时接口的压力；
下单同样也是需要幂等，除此之外下单成功锁库存，给订单30分钟有效期，前端配合支付倒计时，超时自动关单释放库存，防止库存被死锁。

还有一个最重要的模块就是支付，支付核心要解决的问题就是：防重复扣款，和超时后的最终一致；防重复扣款通过双Token机制解决：前端幂等Key解决重复提交，后端一次性payToken绑定用户、订单、渠道，解决请求合法性；还有就是超时处理，前端超时一律进入UNKNOWN状态，UI显示"支付处理中"，然后靠持续查单收敛，轮询订单状态接口直到拿到成功或失败；当前后端也需要做一些处理，比如支付单要有事实记录，定时扫描处理太久的单去主动查三方，还有每日对账这些；支付链路我们会维护一个完整状态机：未发起、创建支付、排队、拉起收银台、处理中、成功、失败、取消，加上 UNKNOWN，后端会在高峰期先把支付单入队，叫号再拉收银台。总的来讲，就是幂等提交、后端有事实源、前端超时只认处理中、靠查单收敛终态。

整个电商从商品展示到支付售后比较核心的设计要点就是：用户永远不能看到白屏、服务端才是唯一的事实源、交易操作必须幂等。体验靠分层加载和弱网分级量化到 FCP、LCP；交易用状态机；秒杀抓倒计时、防重、削峰；支付抓双 Token 和查单收敛。


**首页加载策略**
- `分层分优先级`：静态骨架屏 =》p0、P1、P2 =》prefetch预获取（hover 秒杀入口时 prefetch 秒杀会场资源）
- `接口聚合`：Promise.allSettled，兼容没有数据的模块
- `LCP 元素优化`：preload第一张轮播图，广告位大图
- `二次进入秒开策略`：service worker（vite-plugin-pwa + workbox，injectManifest自定义注册assets静态资源）
  - *HTML骨架 + 核心 CSS/JS*：带 contenthash，内容不变就命中缓存
  - *首屏 P0 接口数据，商品图片*：先返旧数据，后台静默拉新数据
  - *支付/结算/账户安全页*：涉及资金安全，不走缓存
- `弱网分级处理`：图片低清、接口聚合、关闭动效
- `性能指标控制策略`：按网络和机型分桶，75分位/90分位数据



**商品列表滚动加载技术难点**
1. `大量 DOM 节点导致卡顿`：分页预取下一页，组件 memo 缓存，图片懒加载，数量>200虚拟列表（估算高度、高度缓存、二分查找、滚动越快前后预渲染越多）、web worker处理计算逻辑
2. `图片加载引起的 CLS`：商品卡片图片固定宽高比（img-wrapper:aspect-ratio=1/1 + img:loading="lazy"）
3. `滚动位置恢复`：本地缓存滚动scrollY和page，返回时恢复



**弱网与断网容灾**
- *弱网分级策略*：navigator.connection?.effectiveType(Android) + RTT(ios)
  - `良好（RTT<50ms）`：正常加载
  - `一般（RTT<200ms）`：低清图片
  - `弱网（RTT<500ms）`：接口聚合、低清图片、关闭动效
  - `断网（请求失败，window.addEventListener 全局监听 online/offline 事件）`：sw离线缓存，按钮置灰，断网提示，评论/推荐模块隐藏，加入购物车等非关键操作进行“待发送”队列，联网后同步调接口处理
- *请求超时与重试策略*：
  - P0 核心数据：3秒超时，最多重试2次，指数退避重试，失败后用缓存
  - P1 列表数据：5秒超时，最多重试1次，指数退避重试，失败后显示为空
  - P2 推荐/埋点：8s超时，静默隐藏
  - 交易类：不自动重试，10s超时，展示错误 + 手动重试
  - 支付类：绝不自动重试,15s超时，超时后查订单状态



**秒杀页面与倒计时技术难点**

- *倒计时时间同步：*
  1. 获取服务端权威时间：客户端记录本地时间戳 `sendTime` =》接口获取服务端权威时间 =》服务端返回 `T_server`（服务端在响应时的时间） =》 客户端记录收到响应时的本地时间 `receiveTime` =》 计算：`RTT = receiveTime - sendTime; 校正后的服务端时间serverTime ≈ T_server  + RTT / 2`
  > 记录时间偏移：`offset = serverTime - clientTime`，其他日志/埋点等场景可能会用到~
  2. 建立单调时钟锚点：收到响应那一刻，同时记录两个值作为"锚点"：
    - 同一瞬间采的单调时钟读数：`anchorPerfTime = performance.now()`，*performance.now() 单调递增，不受用户改系统时间影响，防止倒计时跳秒、倒流*
    - 校正后的服务端时间：`anchorServerTime = serverTime`；
  3. 倒计时更新；tick频率：250-500ms 一次，临界点（最后 3-5 秒）提高到 100-200ms
    - 计算过去了多长时间 `elapsed = performance.now() - anchorPerfTime`；
    - 当前时间`currentTime = anchorServerTime + elapsed`；
    - 剩下时间`remaining = endTime（秒杀截止时间） - currentTime`
  4. 定期重新校准；performance.now() 相对真实时间有晶振漂移，每天可漂移数百 ms，锚点不能只建一次；校准重新走步骤1-3
    - 每 30min 轻量校准一次；最后 10min 提高校准频率（如每 30s）；visibilitychange（从后台回来）立即重新校准

## 高精地图页面经过多次绘制后，再拖拽页面重新请求接口数据，重新绘制时，就会出现页面卡顿的情况，怎么进行渲染性能优化？
> ai生成

先交代背景。我们地图上要渲染车道级高精数据——每条车道线、每个道路边界，都是几百上千个坐标点。用户的实际体感是什么呢？页面多次绘制之后，再拖一次地图，就会明显卡一下，严重的时候要卡好几秒。

当时我第一反应是：*卡在哪里？*我没有直接猜，而是先加了埋点，把渲染拆成"本地转换"和"mapvgl 绘制"两段，分别计时。测出来的结果很直观：一次渲染，本地转换只占 2% 到 5%，剩下 95% 以上全耗在 mapvgl 的 setData 上，一次就要 3.7 秒，多的时候能到 20 秒。

那为什么 setData 这么贵？查了官方文档，这是 mapvgl 的设计约束：它没有增量接口，你要往里加数据，只能把"历史全部加新增"整份重传。我们实测下来，大概每条数据 5 微秒。听起来不多，但一次要重传几十万条，就是秒级了。

更关键的发现是：我们当时是每个瓦片、每个类型都做一次全量重传——同样一批数据，被重复处理了十二倍。打个比方，就像搬家，本来一车能拉完的箱子，我们来回拉了十二趟。

所以根因用一句话总结：耗时等于数据量乘以单价，而我们的数据量被重复放大了十几倍，而且只增不减——拖得越多，历史数据越多，每次重传就越贵。

基于这个结论，我们做了四件事。

*第一，聚合。*把一轮请求里的所有瓦片，先按类型归并，每个类型只提交一次。这一步直接把处理量从 76 万条降到了 4.4 万条。

*第二，分帧。*所有对图层的写入，不再一次性同步做完，而是拆成小任务放到 requestAnimationFrame 里，每帧最多干 8 毫秒，干不完下一帧继续。这样哪怕总量要一秒多，主线程也永远有空隙响应拖拽——地图上看到的效果是"逐渐画出来"，而不是"卡完一下全出来"。

*第三，限界。*单个类型的数据量大了，单次提交还是会超时，所以把每个类型拆成 3000 条一个子层，超出就开新层，保证单次操作的耗时封顶在二三十毫秒。

*第四，砍掉重复操作。*图层显隐切换原来每次都要遍历全部图层刷一遍，加了个缓存，状态没变就跳过。

效果怎么样？几个数：单帧最大耗时从 120 到 165 毫秒，降到 33 到 36 毫秒，已经低于浏览器"长任务"的 50 毫秒阈值；图层切换从 300 多毫秒降到接近零；主线程从"一次冻结好几秒"变成"完全感觉不到"。

最后说两句实话。第一，我们做的是"减少次数、限制规模、改变形态"，但 mapvgl 全量替换的单价消不掉，所以还有一道天花板：拖得越远，累计数据越多，重传量就越大——要彻底解决，只能靠后端减量，比如按缩放级别抽稀、只返回视口内的数据，这是我们下一步的方向。第二，整个过程里，所有结论都是先量化、再动手，中间也踩过坑、回退过方案，但原则没变：基于数据，不猜。



**为什么mapvg只有全量方法，没有提供增量绘制的方法呢，这是出于什么考虑呢？**

这个问题我先直接给结论：`这不是 mapvgl 能力上的缺失，而是 API 设计上的取舍——它选择了"简单可控"，放弃了"极致性能"。`可以从三个层面理解。

*第一层，是它的设计哲学。*mapvgl 采用的是"声明式"模型，跟 React 类似：你负责维护状态、把完整的数据交给它，至于怎么渲染、怎么更新，是它内部的事。React 里我们写 setState，也不会去手动 diff 每个节点对不反对吧？mapvgl 的 setData 就是同一个角色——你给它完整状态，它来负责重建。但是这个模型天生的一个代价就是：没有增量的入口——因为库不会去追踪"哪一条数据是新增的、哪一条是删除的"。

*第二层，是增量实现的真实成本*。如果要做增量接口，mapvgl 内部就必须维护一张"数据项和渲染对象的映射表"——每一条数据对应哪个顶点缓冲、哪个 mesh。一旦支持增删改，就要处理：数组插入后所有索引的漂移、包围盒要重新计算、点击拾取的命中编号会变……这些全是牵一发动全身的活，实现复杂度比"全量重建"高一个量级，而且很容易出 bug。对库的维护者来说，这个性价比不划算。

*第三层，是场景匹配度。*地图瓦片的使用模式是什么？一次请求、批量加载——我拖一下地图，后端给我几万条数据，我一次性提交进去。在这种场景下，全量替换的代价是可控的。而增量接口真正的价值场景是"高频、单条修改"——比如一个实时数据看板，每秒更新一条。但那是图表库的活，不是地图渲染的主链路。mapvgl 是为"批量加载"优化的，不是为"单条编辑"优化的。

当然，它也不是完全没有轻量操作——setOptions 改样式、show/hide 显隐、clear 清空，这些都是轻量的，缺的只是"数据级"的增量。

所以回到我们项目的应对思路就很清晰了：既然全量替换消不掉，我们就从三头下手——把全量次数压到最低（聚合）、把单次规模限住（子层化）、把执行摊进多帧（时间切片）——在框架的约束下，把性能挖到极限。
